# 1.1.5 / 1.1.6 设备后端版本规划

> 规划日期：2026-09-12。
> 状态：用户已确认版本方向；本文是待实施规划，不是实现完成、实机通过或发布记录。
> 本文是 [开发总计划](DEVELOPMENT_PLAN.md) 的版本分项，后端迁移的详细任务与发布门槛以本文为准。
> 写入规划不修改当前 `VERSION`，不触发部署、卸载 ModemManager 或停止设备服务。

## 1. 已确定的版本方向

| 版本 | 定位 | ModemManager | 原生后端 | 交付结果 |
| --- | --- | --- | --- | --- |
| 1.1.4 修复线 | 收口现有 IMS、生命周期及必要回归 | 保持当前实现 | 不在修复中夹带全面替换 | 给后续迁移留下可对照、可回滚的基线 |
| **1.1.5** | **统一设备接口与双后端过渡** | 保留为可选后端 | 实现并验收 QMI / MBIM / AT 适配 | 上层 UE/IMS 不直接依赖 MM；已有设备可以受控迁移到原生后端 |
| **1.1.6** | **原生后端独立接管** | **移除后端实现、运行调用、必装依赖和 MM 专属恢复流程** | 接管本版本支持清单中的全部 modem 能力 | 在未安装 MM 的环境完整运行，不保留 MM 开关或隐藏回退 |

两项定义必须统一：

1. **“双后端兼容”不是两个后端同时控制同一物理 modem。** 1.1.5 可在不同设备上分别使用 MM、原生后端；一台 modem 的所有槽位、线路及端口由同一个设备控制器协调。
2. **“全部原生接管”指本项目明确承诺支持的设备及能力全部脱离 MM。** QMI、MBIM、AT 三类传输都在目标范围内；不是未经适配就宣称兼容世界上所有基带、固件和 USB 组合。

1.1.6 移除 MM 是本规划的确定目标，不是可选建议。若原生覆盖或关键回归未完成，应延后发布；不能悄悄保留 MM 兜底，或静默缩减支持清单来宣称目标完成。

## 2. 范围与非目标

### 纳入迁移

- modem/端口发现、设备生命周期、物理槽位、SIM/eSIM 身份与线路映射。
- 蜂窝驻网、信号、接入制式、运营商选择、漫游状态、飞行模式及已支持的无线控制。
- SIM/APDU/AKA 所需的设备访问、AT 会话及 QMI-UIM 等通道的统一协调。
- IMS 与普通数据 bearer 的建立、配置、状态、释放、取消、异常退出恢复。
- 原生短信与原生电话的现有控制能力，及依赖这些能力的 API、通知和自动化。
- 配置迁移、诊断、安装、升级、卸载、systemd 和设备恢复资源。

### 保留的架构与功能边界

- 强制 per-UE worker/netns 架构不变，不允许退回宿主网络注册来制造成功。
- `line_id` 继续代表稳定物理槽锚点/UIM slot 或读卡器线路；SIM 覆写继续跟随 `SimBindingKey`。更换后端不能改变这些语义。
- 用户态 SIP/IMS、VoWiFi、媒体与业务编排不因换后端而重写协议栈。
- PC/SC 读卡器、独立 SIM/eUICC 线路不能被强制要求具有 QMI/MBIM 端口。
- 去 MM 不等于去 system D-Bus、libqmi、libmbim、qmi-proxy 或 PC/SC；这些依赖分别评估。
- 不顺带宣称完成尚未验收的 VoNR、CS 双向音频/Trunk、MEP、E911、视频或补充业务。它们仍按开发总计划单独验收。

## 4. 目标架构与硬约束

### 4.1 统一接口，设备控制器协调传输

```text
API / 自动化 / 线路服务 / 用户态 IMS、VoWiFi 与 UE worker
                         │
                  统一设备能力接口
                         │
          稳定设备/槽位绑定 + 单一设备控制器
                  ┌──────┴──────┐
        MM provider             Native provider
        仅保留到 1.1.5          1.1.5 引入，1.1.6 唯一接入
                                    │
                             设备 driver 策略
                           ┌────────┼────────┐
                       QMI adapter MBIM adapter AT session
```

QMI/MBIM/AT 是底层协议适配器，不必与设备一一对应。例如一台设备可能使用 QMI 数据面和 AT 控制；它们必须由同一个 native controller 协调，不能成为几个互相抢端口的独立管理者。

建议按实际调用点提取以下能力，不预建没有实现、没有调用方的大量 stub：

| 能力 | 接口应提供的结果 |
| --- | --- |
| discovery / identity | 稳定设备标识、端口组、槽位、SIM 绑定与当前设备 generation |
| radio / network | 驻网、home/visited PLMN、RAT、信号、支持的控制及事件 |
| SIM access | APDU/鉴权能力、逻辑通道、槽位归属、命令串行化 |
| bearer / data | 地址、前缀、网关、DNS、P-CSCF、专属接口、opaque handle 与生命周期 |
| messaging / native call | 发送结果、接收/状态事件和结构化错误；与用户态 IMS 业务分开 |
| lifecycle / diagnostics | 健康状态、受控恢复、资源归属、取消、关闭、重连原因与计数 |

接口名称和模块拆分由实施阶段的设计评审确定；上表不是当前已经存在的 Rust API。

### 4.2 不可破坏的契约

1. **单一控制权**：同一物理 modem 同时只能有一个设备控制器，覆盖全部端口与线路。MM 与 native 不可争用同一设备；native 内 QMI/MBIM/AT 的访问也要协调。
2. **稳定身份**：MM `/Modem/N`、`/Bearer/N`、临时 `wwanN` 编号不作为持久化线路/SIM 身份。后端切换、枚举变化、换卡和 eSIM 切换必须分别处理。
3. **控制面与数据面分离**：控制器可留在宿主；经验证独占的 IMS 数据接口仍进入对应 UE。禁止接管其他线路、管理网络或其他程序正在使用的接口。
4. **能力明确**：支持、不支持、未知/待探测分别表达。缺失能力必须给出原因，不伪造 QMI 路径、注册状态或宿主网络兜底。
5. **策略不变**：保留 profile 选择、IPv4/IPv6 回退、漫游、短信/通话路径和费用相关意图；不为某张 SIM 写死身份、P-CSCF 或地址族。
6. **生命周期完整**：创建中取消、失败回滚、正常关闭、崩溃恢复、基带重枚举和旧 generation 回收均有边界；不能清理新实例或其他 owner 的资源。
7. **恢复有界**：只对归属明确的设备执行有界恢复；禁止无限重试、无提示全局重启、因一条线路失败重启所有设备。
8. **诊断分层**：设备发现、端口、承载、路由、SIP、AKA、续期和业务分别报告，不能把本地通道错误一概解释为运营商拒绝。
9. **保密与权限**：日志不泄露完整 SIM/用户标识或认证材料；归属账本保持最小内容、受限权限和原子写入。

QCA410 的已验证接入约束仍作为迁移基线：主 QMI 用于 IMS，DATA6 用于普通数据。换成 native provider 不构成恢复旧 DATA6 IMS 路径或把该布局推广到其他设备的理由。

## 5. 1.1.5：双后端过渡版本

### 5.1 目标

**把 MM 从上层的事实前提，变成统一接口的一种实现；原生后端可以独立完成已声明支持设备的能力。**

- 保留 MM provider，供兼容、对照和受控回滚使用。
- 引入 native provider 及 QMI、MBIM、AT 适配，按真实设备能力组合。
- 既有部署升级时保持原选择，不能静默切换底层 owner。
- 原生设备验收通过后，才允许对明确的设备/固件组合选择 native。
- 后端选择是设备管理层策略，不增加 QCA410 IMS 接口猜选开关，不改成每条业务各选一个控制者。
- 切换后端需要维护窗口：无活动通话，释放 bearer、SIM 逻辑通道、接口和归属后再交接；不热切正在续期或通话的会话。
- 连接失败先在原 backend 内分类处理；不得自动争抢式切到另一 backend，并把新注册冒充原会话续期。

### 5.2 实施里程碑

| 阶段 | 待办与交付物 | 阶段门槛 |
| --- | --- | --- |
| M0：基线与设计 | [ ] 冻结目标设备/固件/能力矩阵；枚举全部 MM 调用；形成接口、身份迁移、依赖与恢复的设计决策 | 支持范围和测试资源明确；已知旧卡/IPv6 问题有独立记录 |
| M1：MM 适配器收口 | [ ] 现有 MM 功能经统一接口调用；线路、API、IMS、消息事件逐批迁移 | 同设备/卡/配置下行为不回退，未迁移调用有清单而非隐藏路径 |
| M2：QCA410 原生闭环 | [ ] 独立 discovery、无线/SIM 访问、QMI bearer、UE 数据面、生命周期和已有业务控制 | 无 MM 服务时完成实际注册/续期及故障恢复，不只拿到 IP |
| M3：其他原生适配 | [ ] 完成目标 Quectel 等设备的实际 QMI/MBIM/AT 组合；保留 PC/SC 线路 | 三类传输均有真实接线和硬件证据，不用 mock 代替整个后端 |
| M4：运维与兼容 | [ ] 后端选择/状态可见；安装依赖条件化；旧配置迁移；MM↔native 受控交接及回滚 | native 部署不会暗中启动/调用 MM；两类设备混合运行不串线 |
| M5：发布验收 | [ ] 执行第 7 节矩阵，归档差异、已知限制和每设备默认后端 | 所有 1.1.5 声明支持项有证据；1.1.6 剩余差距逐项列出 |

原生实现优先评估复用 libqmi/libmbim 等成熟库。常驻会话、事件循环和命令协调必须有明确 owner；不能把散落的短命 qmicli/mbimcli 命令当成完整设备管理实现。若采用 FFI 或受控协议进程，需先验证 arm64/amd64、musl/系统库兼容与打包方案。

### 5.3 发布门槛

- [ ] MM provider 的既有声明能力无回退，MM 专属细节不再从上层编排泄漏。
- [ ] QMI / MBIM / AT 各至少有一套真实适配证据；本版声明为 native-ready 的设备，在未安装 MM 的环境完成相应能力验收。
- [ ] 同机两个不同 modem 分别使用 MM/native 时，身份、接口、事件和清理互不影响。
- [ ] 同一 modem 的双 owner 冲突被明确拒绝，后端交接与包级回滚通过。
- [ ] 已保存的线路配置、SIM 覆写、通知、自动化、Trunk 绑定和历史记录不因后端变化错绑。
- [ ] UI/API 可辨认所选/实际 backend、driver、能力、失败阶段及恢复状态，不泄露私密标识。
- [ ] MM 必装依赖、启动 debug override、恢复服务均已条件化；纯 native 部署不会拉起 MM。
- [ ] 无编译、协议回归和必要实机回归失败；不能仅靠编译选项或页面显示宣称“MM 可选”。

## 6. 1.1.6：完全原生接管版本

### 6.1 目标

**生产代码不再把 ModemManager 当作可选 backend；所有声明支持的 modem 能力由 native provider 接管。**

这不是“默认 native、保留 MM 隐藏开关”，也不是“只去掉 IMS 对 MM 的依赖”。

### 6.2 必须完成的移除与替代

| 阶段 | 待办与交付物 |
| --- | --- |
| N0：补齐覆盖 | [ ] 逐设备清除 1.1.5 的 native 能力缺口；完成原生短信、原生呼叫及依赖它们的 API/自动化迁移 |
| N1：删除 MM runtime | [ ] 删除 MM provider、mmcli 调用、MM D-Bus 接口/信号监听、MM 对象路径驱动的发现及控制；清除旧能力兜底 |
| N2：删除运行依赖 | [ ] 安装包不再安装/拉起 MM；删除项目的 MM debug override、Wants/After 和专属探测/恢复逻辑；native recovery 接管设备健康 |
| N3：迁移产品接口 | [ ] 移除 backend=MM 的选择入口、文档指令和运行开关；旧配置有一次性转换或明确迁移错误，不能静默忽略 |
| N4：原生运维闭环 | [ ] 无 MM 环境下冷启动、长稳、热插拔、SIM 切换、取消、崩溃恢复、升级及回滚通过 |
| N5：发布核验 | [ ] 生产调用/进程/包依赖审计和真实硬件矩阵通过，确认没有隐藏 MM 回退 |

移除 MM 后端不代表安装器有权全局卸载用户的 MM 或影响它管理的其他设备。若外部程序仍占用 SimAdmin 要接管的设备，应明确报告占用并要求安全交接，不能全局停服务或抢端口。历史文档、旧配置迁移数据和外部占用提示可以提到 MM，但不能保留运行时兼容调用。

### 6.3 发布门槛

- [ ] 目标系统不安装 MM/不提供 MM D-Bus 服务，应用仍完成启动、发现及支持矩阵内全部功能。
- [ ] 安装、启动、API、后台轮询、SIM/eSIM 操作、自动恢复、卸载流程均无 MM 调用/依赖；非设备用途的 system D-Bus 另行核对。
- [ ] QMI / MBIM / AT 三类原生适配完成各自契约和真实设备测试，所有声明支持的设备/固件无 MM 必需能力残留。
- [ ] 无后端选择项、环境变量、故障兜底或自动安装路径重新启用 MM。
- [ ] 原生模式的资源释放、受控恢复和多线路隔离不弱于 1.1.5 已验收基线。
- [ ] 旧配置迁移、数据一致性备份、维护窗口内升级和回滚演练通过。
- [ ] 支持矩阵与实际能力一致。任一承诺项未通过则阻止发布；支持范围变更需显式确认并写入版本说明。

## 7. 设备范围与验收矩阵

### 7.1 设备范围：M0 冻结，未经确认不扩称

| 设备/接口类 | 规划覆盖 | 冻结与验收要求 |
| --- | --- | --- |
| QCA410 / MSM8916 类 | 优先完成原生 QMI + 必需 AT/UIM 协调、BAM-DMUX 映射、IMS/普通数据隔离 | 区分固件、libqmi/内核组合；复测 SIM-01/02/03，不以 SIM-03 IPv4 成功替代 IPv6 |
| EC20 / EC25 / EG25 家族 | 纳入既有设备扩展目标，按真实 QMI/AT 组合适配 | 型号相近不等于接口、无线控制和音频能力相同；逐型号保留证据 |
| EG600 等 MBIM/QMI 设备 | 按实际 USB/PCIe 和固件模式选择原生协议组合 | M0 明确真实测试样本；至少覆盖一个真实 MBIM 运行组合，不凭“5G”宣称 VoNR |
| AT 控制设备/通道 | 直接 AT、URC、串行化、SIM/无线及所声明的原生业务控制 | AT 可与 QMI/MBIM 组合；若声明 AT-only 数据连接，必须另验真实 PPP/ECM/NCM 等数据面 |
| PC/SC SIM/eUICC 读卡器 | 保留独立线路与现有 SIM/eSIM 能力，不强加 modem 后端 | 无卡、PIN 锁卡、AKA、热插拔及声明支持的 profile 操作分别验收 |
| 未识别/未支持设备 | 明确 unsupported/能力不足 | 不猜接口、不借其他 modem 的端口、不隐式回到宿主网络或 MM |

当前未获得的硬件与固件是计划依赖，不是通过项。M0 必须记录具体型号、固件、内核、端口组成、协议模式和可验证能力；不能用“其余所有设备应该类似”代替清单。

### 7.2 各版本共用的测试门槛

| 领域 | 必须验证 |
| --- | --- |
| 发现与身份 | 冷启动、热插拔、同 PLMN 不同 SIM、换卡、eSIM 切换、端口重新编号、稳定 line_id 和 SIM 覆写归属 |
| 单 owner 与并发 | 两进程争用、MM/native 冲突、两台 modem 混用后端、同一控制器的多槽位/多业务协调 |
| 承载与路由 | IPv4、IPv6、双栈与网络强制单栈；地址/前缀/网关、IPv6 地址就绪/DAD、P-CSCF 路由、MTU、UE 移入/移出和失效清理 |
| IMS 注册 | 身份派生和库选择、真实 AKA、网络租期协商、实际协商的 UDP/IPsec，以及失败分类 |
| 自然续期 | 每个声明支持的 IMS 测试组合至少两次自然续期；保持原会话/通道和相应安全关联，reconnect 不增长；不缩短租期或重注册凑数 |
| 长期稳定 | 各目标硬件/固件组合至少一个代表场景连续 24 小时；记录掉线、重建、资源泄漏、CPU/内存及事件队列增长 |
| 生命周期 | setup 取消、连接中退出、正常关闭、主进程强制终止、设备失联/重枚举、陈旧归属、恢复失败和有界重试 |
| 业务 | 对声明支持项分别验证 IMS/原生短信、IMS/原生呼叫控制、普通数据、代理、通知和自动化；不把控制成功当双向音频通过 |
| 数据库/profile | 固定同卡/固件/接入条件对照 iOS、Pixel 等有效 profile；核对 INVITE 是否抵达、拒绝原因与路由，不以注册代替呼入验收 |
| 多 UE 隔离 | 至少两条真实线路；一条失败/停止/恢复时另一条的会话、路由、SIM 鉴权、消息和通话不受影响 |
| 配置与安全 | 原子迁移、WAL/备份一致性、磁盘满/只读、权限和敏感日志检查；owner/generation 校验不能只用可复用的 PID/编号 |
| 工程与发布 | provider 契约测试、故障注入、arm64/amd64 构建、native 无 MM 环境测试、安装/升级/卸载及旧版回滚 |

网络或硬件确实不支持的项可标记 N/A，但必须有能力证据和替代测试覆盖；不能将未测试或缺少硬件标记为通过。1.1.5 的 MM/native 对照必须控制卡、固件、网络、profile 和地址族条件。

真实通话/短信须使用获得授权的测试方式；不自动拨打电话、发短信、改变资费策略或拨打紧急号码。每次测试的版本、硬件、脱敏 SIM 标签、backend、effective profile、实际地址族、会话标识、计数和结论分别记录。

## 8. 升级、交接与回滚

1. **建立可回滚基线**：1.1.4 当前修复与旧卡回归独立收口；迁移试验不能覆盖原修复证据或提前宣布已验收。
2. **优先升级路线为 1.1.4 → 1.1.5 → 1.1.6**：先在 1.1.5 校验身份映射、原生能力与配置，再切换 native；不能只改一个 backend 字段就认定交接完成。
3. **交接前释放旧资源**：确认没有活动通话，保存一致性备份，由旧 owner 释放 bearer、SIM 通道、UE 接口和归属。不能让 1.1.6 为清理旧资源重新依赖 MM。
4. **配置保持**：物理线路配置留在原槽位，SIM 覆写跟随原 SIM 键；保存通知、自动化、Trunk、网络与费用策略。不以新枚举编号创建重复线路。
5. **旧选择的处理**：1.1.5 保留原 backend；升级 1.1.6 前运行迁移检查。旧 MM 选择只允许经验证转换成 native，能力不足时给出可操作的阻断原因，不隐藏回退。
6. **直接跨版升级**：若没有证据证明旧资源已释放、映射可迁移、原生能力满足，必须阻止直接跳到 1.1.6，提示先完成过渡步骤。
7. **回滚是包级维护操作**：备份对应旧版本、数据库和资源策略，清理新 owner 后再恢复；不是 1.1.6 内置运行时 MM fallback，不覆盖用户无关配置或卸载无关服务。

## 9. 交付与执行规则

- 本文各实施项当前均待完成。一个事项必须分别记录“代码实现、CI、实机、发布”，不能只勾选笼统“完成”。
- `DEVELOPMENT_PLAN.md` 维护总优先级和本规划入口；本文维护版本后端明细；发布后再把用户可见结果写入 `releases/` 和 `CHANGELOG.md`。
- 先做 M0/M1，不在当前 IMS 修复分支直接混入大规模 native-only 改造。版本号、分支、依赖删改和发布必须在正式启动相应实施阶段时处理。
- Rust 编译/测试/产物验证沿用项目 CI 约束；本规划不授权在设备上执行破坏性实验，也不因缺少 MM 就自动安装或移除系统服务。
- 迁移风险集中在硬件差异、稳定身份、多个协议争用、IPv6/namespace 时序、SIM 逻辑通道、异步事件和崩溃后的资源归属。依赖数量减少不自动等于鲁棒性提升。
